01System overview

A multi-tenant restaurant operations platform: anonymous guests order via table QR codes, seven staff roles run the floor, kitchen, menu, inventory and procurement, and AI agents can connect through a built-in MCP server. One codebase, one Supabase project, no separate backend service.

The single most important architectural fact: the Cloudflare Worker only renders HTML and hosts the MCP endpoint. All application data access happens directly from the browser to Supabase using the public (publishable) key — there are zero server-side data routes, zero .rpc() calls, and no privileged service key anywhere in the codebase. Every guarantee about who can see or change what rests on Postgres Row Level Security, plus two database triggers that hold the only server-side business logic.

The core loop that actually works end-to-end: guest scans QR → anonymous session → orders from a themed or Canva-designed menu → kitchen advances items (pending → preparing → ready) → waiter delivers (→ served) → a DB trigger deducts recipe ingredients from inventory, writes the consumption ledger and arms low-stock alerts → shopping list → purchase order → goods receipt restocks. Payments, POS delivery, ERP sync and AI import are staged UI shells around this loop (see the maturity map).

Server-side logic (the only two places)

  • deduct_inventory_on_serve — AFTER UPDATE on order_items: on transition to served, atomically decrements each recipe ingredient’s stock, writes inventory_log (order_consumption), and touches matching active low-stock alerts.
  • enqueue_pos_event — AFTER INSERT/UPDATE on orders: queues order.open / order.update / order.void / check.close into pos_event_queue when the restaurant has a connected POS integration. (Nothing drains the queue.)

05Architecture decisions that define the system

  1. RLS is the entire security model. Every query runs in the browser with a public key (staff add their JWT). Client-side route guards are UX, not security. The repo’s own policies (inventory, payments, canva) follow a consistent three-tier pattern — admin / franchise client / restaurant staff — but the core-domain policies live only in the hosted database.
  2. SSR shell, client data. TanStack Start on Cloudflare Workers renders pages, but no route loader or server function touches data. React Query is provisioned per request yet effectively unused by feature code — components fetch with useEffect+useState and refetch-on-mutation.
  3. Anonymous-by-design guests. Customers never authenticate. Identity = localStorage bundle + DB-issued guest_token stamped onto orders; attribution (whose orders on the bill) is by token match. Cheap and frictionless; also the root of the payment-trust gap.
  4. Item-level order lifecycle. Kitchen and waiter operate on order_items.status (pending→preparing→ready→served); order-level completed exists only in the guest “payment” flip. No staff screen ever closes an order.
  5. Where computation lives: order-driven stock math → DB trigger (atomic); staff actions (receive PO, waste, stock take) → client-side read-modify-write loops (non-transactional, race-prone); analytics/KPIs → client-side reduction over fetched rows (franchise revenue fetches every order; owner KPIs sample last 50).
  6. The app is an AI-agent backend. The MCP server exposes read-only ops data behind OAuth with the user’s own JWT forwarded to Postgres — agents automatically inherit exactly the user’s RLS permissions. The most forward-looking decision in the codebase, and it required no new authorization model.
  7. Staged vitrine strategy. Payments (“Phase B”), POS adapters (“Phase C”), ERP sync, and AI import all have finished UI + schema but no engine — the schema (event outbox, transactions ledger) is deliberately dispatcher-shaped, waiting for a server-side worker that doesn’t exist yet.
  8. Config-over-code menu presentation. One restaurant_menu_config row per restaurant switches template (classic vs Canva), theme, and layout; both the Customiser and TemplatePicker upsert the same row (a known overwrite race).
  9. Manual-SQL migration culture. Four idempotent SQL-editor scripts, no supabase CLI chain, no baseline; plus two auto-generated MCP route files owned by the Lovable Vite plugin. The database, not the repo, is the source of truth for schema.

06Maturity map — what is real vs vitrine

Real and demonstrable today: the full guest→kitchen→waiter→inventory loop with live updates; QR provisioning and printing; menu authoring (items, sections, theming, CSV import, PDF-based Canva import); procurement (suggested orders → PO → receipt); stock takes, waste, alerts, analytics and exports; multi-tenant admin with role scoping; the MCP server.
Vitrine (looks enterprise, no engine): payment processing (no processor — guests settle by flipping order status), POS sync (outbox fills, dispatcher absent), ERP sync (config + self-written log only), AI import (disabled tab). Demo narratives should not lean on these four.
  • Dead code: RoleStubPage, clearGuestSession, legacy Canva token path (saveParsedDesign), placeholder move/resize, payment.captured enum member, unused admin bulk-select.
  • Identity trivia: the app carries three names — package tanstack_start_ts, Worker tanstack-start-app, user-facing “Restaurant POC” (meta description even says “Cloud Connect”).
  • No tests, no CI anywhere; quality gates are eslint + prettier.

07Risks & gaps, ranked

  1. Client-authoritative money. Order prices/totals come from localStorage; the anonymous guest browser can UPDATE orders to completed (“paying” without paying), and /check is table-scoped, so a guest can close a previous party’s orders. Tax/tip hardcoded 0; no payment record is ever written.
  2. Repo cannot rebuild the system. ~35 of 42 tables, all anon policies, helper functions, the invite trigger, and one bucket exist only in the hosted Supabase project. Any environment loss or fork depends on exporting the live schema first.
  3. Plaintext third-party credentials in row-readable tables. pos_integrations.config (readable by all restaurant staff per its own RLS) and erp_integrations.config hold API keys/secrets with no vault; they also transit the browser.
  4. Tenant-boundary soft spots. menu-canva bucket writable bucket-wide by any authenticated user; inventory read policies expose restaurant_id IS NULL rows to everyone; /kitchen has no role guard and no restaurant scoping; unfiltered realtime subscriptions (kitchen-board, order_items, waiter_sessions) lean entirely on live-DB RLS.
  5. Non-transactional multi-step writes. Order + items insert, PO receiving, stock-take completion, waste logging, join-table delete-then-reinsert (tags/ingredients), Canva design save — all can fail mid-sequence and leave inconsistent state; stock updates from staff actions are read-modify-write races.
  6. Unbounded growth. pos_event_queue accumulates forever once any integration is “connected”; waiter shift sessions leak open on crashes; deleted Canva designs orphan storage files.
  7. Correctness papercuts. Owner KPIs sample last 50 orders; two different “today” definitions (local vs UTC); recipe values overwritten by the menu editor (qty=1); imported items can vanish (category↔section string mismatch); template-choice overwrite race; cart survives across restaurants; participant count inflates split math; hardcoded admin email fallback; hardcoded Supabase keys in six files (publishable — configurability issue, not a leak).
